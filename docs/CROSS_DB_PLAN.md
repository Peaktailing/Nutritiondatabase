# 跨库交叉比对：规划与可行性实测

> 本文档所有数字均为**在当前 nutrition.db 上实测所得**，不是估算。
> 目的：在动手写比对功能前，先搞清楚「能不能对得上、对得上多少、对错了会怎样」。

---

## 一、结论先行

| 问题 | 实测答案 | 含义 |
|------|---------|------|
| 食物名精确匹配能对上吗？ | **0%** | 各库食物名语料形态完全不同，必须做语义匹配 |
| 归一化后能对上多少？ | UK 8.9% / FR 9.6% / USDA-FND 4.0% / USDA-SR 8.7% / USDA-SURV 8.5%，**合并 16.7%** | 精确归一化仍然很��，主要卡在中英翻译与描述粒度 |
| 模糊匹配召回率？ | UK 21.0% / FR 31.1%，**合并 35.1%** | 召回能到 35%，但**准确率不可用**（见下） |
| 模糊匹配准确率如何？ | ❌ **不可用**：`黄油 → Cocoa butter`(可可脂)、`奶油 → Soy cream`(豆奶油)、`全脂奶粉 → Milk shake`(奶昔) | 直接入库会产生**误导性结论**，比不做更危险 |
| 中国库可参与比对的条目 | 1,241 / 1,677 有英文名（**74.0%**） | 另 436 条无英文名，需先补译才能比对 |
| 中国库「食物状态」是否可得 | ✅ **可得，默认生/鲜**（92.7% 无加工动作词） | **已解决**（详见 3.3，用户判断经实测验证） |
| 状态带来的例外 | ⚠️ 约 116 条乳制品/油脂需隔离 | 含水 ≤15% 兜底判定为浓缩品，单独成组 |

### 核心判断

1. **「全量自动交叉比对」不可行。** 模糊匹配 35% 的召回里混着系统性误配，直接使用会产生错误的跨国营养结论。
2. **可行的形态是「人工审定的映射表」。** 先由算法产出候选对，人工确认后入库；比对结果只覆盖被确认的映射对。
3. **必须先做「营养素列归一化」**，否则连数值都没法并排放。
4. **状态（生/熟/干/鲜）必须纳入匹配键**，否则比对结果没有营养学意义。
   —— ✅ 中国库这一维度已解决：默认生/鲜，例外仅约 116 条乳制品/油脂。

## 二、实测过程与发现

### 2.1 语料形态：同一种食物的五种写法

| 库 | 食物名示例 | 条数 |
|----|-----------|------|
| 中国 FCT 第6版 | `苹果` / `Apple` | 1,677（英文名 1,241） |
| 英国 CoFID | `Apples, raw, flesh only` | 31,757（唯一名 2,882） |
| 法国 CIQUAL | `Apple, flesh and skin, raw` | 3,484（唯一名 3,389） |
| USDA foundation | `Apples, red delicious, with skin, raw` | **仅 469** |
| USDA sr_legacy | `Pie, Dutch Apple, Commercially Prepared` | 7,793 |
| USDA FNDDS survey | `Cake or cupcake, apple` | 5,432 |
| USDA branded | `11.5 FL OZ JUICE DRINK - APPLE CRANBERRY` | 1,999,950 |

**USDA 只有 469 条 foundation_food 是「一条食物一个规范名」的干净语料**，其余 210 万条是复合食品（蛋糕、混合菜、品牌商品），无法与单食材比对。
→ 结论：USDA 侧应以 `foundation_food` + `survey_fndds_food` 为主力，`branded_food` 排除。

### 2.2 归一化实验：状态词 + 部位词 + 词干还原

从各库名称中剔除状态词（raw/cooked/dried/…）、部位词（flesh/skin/seed/…）、修饰词（red/var/type/…），再做简单词干还原，生成「签名」精确匹配：

```
UK        2,661 签名   → 命中 110 (8.9%)
FR        2,991 签名   → 命中 119 (9.6%)
US-FND      379 签名   → 命中  50 (4.0%)
US-SR     6,970 签名   → 命中 108 (8.7%)
US-SURV   4,886 签名   → 命中 105 (8.5%)
合并                      → 命中 207 (16.7%)
```

命中率反而比模糊匹配低很多 —— 说明**大部分中国食物的英文名在英/法/美语料里根本没有对应项**（不是写法差异，是食物定义本身不同）。
抽查命中样例（这部分质量是好的）：
```
全脂奶粉        Whole milk powder        → Milk powder, whole          ✅
羊乳           Goat milk                 → Goat milk, whole, raw      ✅
黄豆［大豆］     Soybean                   → Soybean, seed, whole       ✅
```

### 2.3 模糊匹配实验：召回 35%，但污染严重

用「最长词作锚点 + SequenceMatcher 相似度 ≥ 0.5」：

| 目标库 | 召回 |
|--------|------|
| UK CoFID | 261 / 1241（21.0%） |
| FR CIQUAL | 386 / 1241（31.1%） |
| **合并** | **436 / 1241（35.1%）** |

**但准确率不可接受**，实测错误样例：

| 中国食物 | 匹配到 | 问题 |
|---------|--------|------|
| 黄油（Butter） | Cocoa butter | **可可脂 ≠ 黄油** |
| 奶油（Cream） | Soy "cream" | **豆奶油 ≠ 奶油** |
| 奶油（Cream） | Cream, half, fresh | 「half」是浓度修饰，未处理 |
| 全脂奶粉 | Milk shake, powder | **奶昔 ≠ 奶粉** |
| 全脂羊乳粉 | Milk shake, powder | 同上 |

> 误配集中在**乳制品、油脂、调味品**——这些恰好是营养差异大、误配后果严重的品类。
> **结论：模糊匹配结果只能作为「候选」给人看，不能直接作为数据入库。**

## 三、必须先解决的前置问题

### 3.1 营养素列归一化（五套命名体系）

当前各库列名体系互不相同，必须建立映射表才能并排比较数值。

| 目标营养素 | 中国 FCT | UK CoFID | FR CIQUAL | TKPI | ASEAN/WAFCT | 日本 MEXT |
|-----------|---------|----------|-----------|------|-------------|-----------|
| 能量 kcal | `energyKCal` | `energy_kcal__kcal` | `energy_regulation_eu_no_1169_2011__kcal_100g` | `energy_kcal` | `energy_kcal` | `ENERC_KCAL` |
| 蛋白质 | `protein` | `protein__g` | `protein__g_100g` | `protein_g` | `PROCNT` | `PROT-` |
| 脂肪 | `fat` | `fat__g` | `fat__g_100g` | `fat_g` | `FAT` | `FAT-` |
| 碳水 | `CHO` | `carbohydrate__g` | `carbohydrate__g_100g` | `carbohydrate_g` | `CHOAVLDF` | `CHOAVLDF-` |
| 膳食纤维 | `dietaryFiber` | `fibre_total__g` | `fibre__g_100g` | `fiber_g` | `FIBTG` | `FIBTR` |
| 钙 | `Ca` | `calcium__mg` | `calcium__mg_100g` | `calcium_mg` | `CA` | `CA` |
| 维生素C | `vitaminC` | `vitamin_c__mg` | `vitamin_c__mg_100g` | `vitamin_c_mg` | `VITC` | `VITC` |
| 钠 | `Na` | `sodium__mg` | `sodium__mg_100g` | `sodium_mg` | `NA` | `NA` |

**注意两个坑**：
- CIQUAL 有**两套能量值**（`energy_regulation_eu_no_1169_2011` 与 `energy_n_x_jones_factor_with_fibres`），必须选定一套并在表里标明，否则同一食物出现两个能量。
- 中国库碳水 `CHO` 是「可利用碳水」，CoFID/CIQUAL 的 `carbohydrate__g` 含膳食纤维差值口径，**直接相减会产生系统性偏差**。需在比对结果中标注口径。

### 3.2 基准与单位统一

| 库 | 数值基准 | 单位风格 |
|----|---------|---------|
| 中国 FCT | 每 100g 可食部 | g / mg / μg（已统一） |
| UK CoFID | 每 100g | g / mg / μg（列名带 `__单位`） |
| FR CIQUAL | 每 100g | g / mg（列名带 `_100g`） |
| 印尼 TKPI | 每 100g | 统一 `_mg` / `_g` |
| ASEAN / WAFCT | 每 100g | INFOODS 裸标签，需查 INFOODS 词典 |
| 日本 MEXT | 每 100g | INFOODS 裸标签 |
| USDA | **每 100g 餐食** | `G` / `MG` / `UG` 混用，**在 nutrient 表里** |

**USDA 的 mg/µg 是大写、亚洲库是小写**，大小写敏感匹配会直接漏掉。USDA 靠 `nutrient.unit_name` 判定，不能看列名。

### 3.3 「食物状态」—— 已解决（2026-10-04 修订）

同样是「苹果」：生食 / 烤熟 / 苹果干 / 苹果汁的能量密度可以差 5 倍。**状态不对齐的比对等于没比对。**

各库状态信息可得性：

| 库 | 状态信息 | 质量 |
|----|---------|------|
| 英国 CoFID | ✅ 名称内含 `raw/cooked/dried` | 完整 |
| 法国 CIQUAL | ✅ 名称内含 `raw/cooked` | 完整 |
| USDA | ✅ 名称内含状态 | 完整 |
| **中国 FCT** | ✅ **默认生/鲜**，见下 | **可用** |
| 日本 MEXT | ⚠️ 名称为日文汉字 | 需日文状态词表 |
| 印尼 TKPI | ❌ 无食物名（仅编码） | 无法判定 |
| 东盟 ASEAN | ❌ 无状态字段 | 无法判定 |

#### 中国库状态判定：默认「生/鲜」（已实测验证）

用户判断：「中国库几乎所有食物都属于新鲜分割或清洗、未加工状态（除烤鸭这类有明确烹饪动作的以外）」。

**实测验证结果——判断成立**：

| 判定方式 | 结果 |
|---------|------|
| 名称含明确烹饪动作（烤/炒/煮/蒸/炸/炖…） | **77 条（4.6%）** |
| 名称含明确加工保藏动作（腊/咸/罐头/糖水/油炸…） | **45 条（2.7%）** |
| **名称无状态词 → 按生/鲜默认** | **1,555 条（92.7%）** |

**含水量交叉验证**（独立于名称的第二重证据）：

| 含水量区间 | 条数 | 占比 | 判定 |
|-----------|------|------|------|
| > 60% | 1,022 | 60.9% | 鲜食 ✅ |
| 15–60% | 243 | 14.5% | 中间态 ✅ |
| ≤ 15% | 348 | 20.8% | 干制/浓缩 ⚠️ |
| NULL | 64 | 3.8% | 油脂/加工品 ⚠️ |

鲜食 + 中间态 = **75.4%**，与名称判定 92.7% 方向一致（名称判定更宽松，因部分干豆/坚果名不带「干」字）。

**→ 结论：中国库可以用「默认生/鲜」作为基线，Q2 无需再讨论。**

#### ⚠️ 但有一类必须单独处理：乳制品与油脂（约 116 条）

这是**「名称无加工词，却不是鲜食」**的例外，也是全库唯一的系统性风险点：

| 类别 | 例 | 含水 | kcal | 问题 |
|------|-----|------|------|------|
| 乳脂制品 | 黄油（0.5%）、奶油（0.7%）、酥油 | **< 1%** | 879–888 | 名称极简但**是高浓度油脂**，与鲜食完全不同量级 |
| 乳粉 | 全脂奶粉、脱脂奶粉、蛋白粉 | 3.7–5.5% | 347–472 | 名字里的「粉」是食材名，不是状态词 |
| 干酪 | 奶酪、干酪、契达干酪 | — | — | 发酵/浓缩制品 |
| 干制豆类 | 黄豆（9.2%）、绿豆（干）、扁豆（干） | 9–14% | 315–407 | 需与「豆芽/鲜豆」（80–90% 水）严格区分 |

**处理方案（已确定）**：

1. 引入**含水量兜底判定**：`water <= 15%` → 标记为 `dried_or_concentrated`，不与「生鲜」条目直接比对
2. 乳制品/油脂单独建 `dairy_processed` 类别，**只在同类内部比对**（奶粉↔奶粉、黄油↔黄油）
3. **这 116 条不参与「生鲜」主流程**，单独成组

#### 状态归一化受控词表（更新后）

```
raw          生/鲜（默认）        ← 中国库 92.7% 落此
cooked       熟/烹饪后            ← 中国库 4.6%
dried        干制                 ← 含水≤15% 判定
concentrated 浓缩/高脂            ← 乳脂、油脂
canned       罐头
salted       盐渍/咸
unknown      无法判定             ← TKPI / ASEAN 全部
```

比对时**只有 `state_match` 一致（或双方均为 raw）才计算差异**。

## 四、已落地的方案：不合并 + 并排 + 公制（2026-10-04 用户决策）

### 4.1 决策内容

用户明确指示：

> **「按照名字和分类排列，不要合并。但是统一所有计量单位到公制。」**

这**推翻了本文档原第四、五部分的「人工审定映射表」路线**。原因与实测依据：

| 原方案的问题 | 实测证据 |
|-----------|---------|
| 跨库实体匹配准确率不可用 | 精确匹配 0%、模糊匹配 35.1% 但系统性误配 |
| 人工审定 100-200 条只是局部覆盖 | 覆盖率 6-12%，无法代表全库 |
| 食物定义差异导致「同名≠同物」 | 「猪肉」在中国是分割生鲜肉，在 CoFID 含脂肪比例口径 |

**改为并排（side-by-side）后，匹配准确率问题从根上消失**：不做实体合并，就没有误配。每条记录保留其来源、原始名称、原始分类，任何"这两条是不是同一个食物"的判断留给使用者自己按名称和分类去看——信息完整，判断权在用户手里。

### 4.2 表结构

```
norm_nutrient     29 个统一营养素（nut_key / 中文名 / 统一单位 / 类型）
norm_canon_cat    15 个统一分类分段
norm_food         并排食物索引（每来源一条独立记录，不合并）
norm_value        公制化数值长表（每食物 × 每营养素一条）
v_by_cat          视图：分类分段 × 来源 分布矩阵
v_browse          视图：分类 + 来源 + 名称 + 公制指标
```

`norm_food` 关键字段：

| 字段 | 含义 |
|------|------|
| `source` | CN / UK / FR / USDA / JP / ASEAN / WAFCT / ID |
| `source_id` | 该库原始编码（可回溯到原始表） |
| `name_local` / `name_en` | 本地语言名 / 英文名 |
| `canon_cat` | 15 个统一分段之一 |
| `cat_raw` | 该库原始分类字段（原样保留） |
| `state` / `state_basis` | 状态判定 + **判定依据**（重要：可审计） |
| `note` | 已知问题标注 |

`norm_value` 关键字段：`value_si`（统一 SI 值，质量类一律 g）、`display_val` / `display_unit`（按营养素习惯显示 mg/μg）、`raw_value` / `raw_unit`（原值留存）。

### 4.3 公制化规则

```
质量类单位 → 一律换算到 g 存储，显示层按需转 mg / μg
  g = 1.0    mg = 0.001    μg = 1e-6    ng = 1e-9

显示单位约定：
  水分/蛋白/脂肪/碳水/纤维  → g
  钙/铁/磷/钾/钠/锌         → mg
  硒/维生素A/维生素E        → μg
  能量                       → kcal（能量不与质量混用）
```

实测：绝大多数原始列已是 g/mg/μg，**唯一的非公制障碍是 IU**（维生素 A/D/E 的国际单位）与 `UMOL_TE`(ORAC)、`MG_GAE`(总酚)、`SP_GR`(比重)、`PH`。这些**保留原值并标注，不做伪换算**——因为换算系数依赖食物类别，强行换算会引入错误。

## 五、构建过程中发现并修复的数据缺陷

这些是**实测中暴露的真实 bug**，记录下来避免重犯：

### 5.1 CoFID 矿物质整体丢失（严重）

`uk_cofid_food` 的 `1.4 Inorganics` sheet 的 A1 单元格是**空格**而非 `Food Code`，导致表头检测失败后 `continue` **静默丢弃整个矿物质 sheet**。

- 修复前：31,757 行 / 267 列，2,813 条食物**没有钙值**
- 修复后：34,644 行 / 279 列

### 5.2 CoFID 行数 ≠ 食物数

34,644 行只有 **2,886 个唯一 `food_code`**（每食物 × 每 sheet 一行）。`norm_value` 主键 `(norm_food_id, nut_key)` 会让同食物的数值互相覆盖，导致 2,886 条里只有 2,886 条有数据（其余 31,758 行白占位）。
→ 修复：按 `food_code` 做 `GROUP BY` + `max()` 聚合。

### 5.3 FR 数值全缺失（类型不匹配）

`alim_code` 是 INTEGER，`norm_food.source_id` 是 TEXT，`idmap` 键匹配失败 → FR 3,484 条数值为空。
→ 修复：`put("FR", str(row[0]), ...)`。

### 5.4 FR 分类颗粒度不足

CIQUAL 只有 11 个粗粒度大组，其中 `meat, egg and fish`（791 条）把三类混在一起、`fruits, vegetables, legumes and nuts`（653 条）把四类混在一起 → 肉类/水产/水果一度全为 0。
→ 修复：组内按英文名称二次细分。

### 5.5 关键词子串误配（隐蔽）

裸 `kw in s` 子串匹配造成两类错误：

| 关键词 | 被误配的词 | 后果 |
|-------|----------|------|
| `pea`（豌豆） | **pear**（梨） | 法国库梨 → 豆类 |
| `ayam`（鸡） | **bayam**（菠菜） | 印尼库菠菜 → 肉类 |

→ 修复：拉丁字母关键词要求左右为非字母字符（词边界匹配）。

### 5.6 中国库括号内状态词被忽略

`栗子（熟）`、`核桃（干）`、`凤尾鱼（熟）` 这类名称用全角括号显式标注了状态，但优先级低于含水量兜底，导致 `栗子（熟）`（kcal 214）被判为生食。
→ 修复：括号内状态词优先级提到最高。

### 5.7 同形异码 μ 导致 2,288 条数值静默丢弃（最隐蔽）

`MASS_TO_G` 字典的键写的是 **µg**（U+00B5 MICRO SIGN），而代码里传的单位字符串是 **μg**（U+03BC GREEK SMALL LETTER MU）。两个字符在屏幕上完全一样，但 Python 判为**不相等**：

```python
'\u00b5g' == '\u03bcg'   # False  ← 视觉上无法分辨
```

后果：字典查不到 → `put()` 里 `if f is None: continue` → **无声丢弃**。中国库的硒（1,223 条）与维生素 A（1,065 条）全部消失，且**没有任何报错**。

修复：
1. 字典同时收录两种写法 + 大写变体
2. 全库源码统一为 U+03BC（26 处）
3. `put()` 增加 `UNKNOWN_UNITS` 记账，构建结束时打印未识别单位——**杜绝再次静默丢弃**

### 5.8 五库胆固醇整体漏映射

`norm_nutrient` 里定义了 `cholesterol`，但只有中国库在 `put()` 里被引用，UK / FR / JP / WAFCT / USDA 五个库的胆固醇列**根本没写进映射**。原始表里合计 8,000+ 条非空值。

### 5.9 东盟分类没有用字母码

ASEAN 的 `group` 形如 `D Vegetables and products (continued)`——首字母是 INFOODS 食物组码，比描述稳定（描述有 `(continued)` 等变体）。原实现只用描述关键词匹配，导致 65% 落入 `other`。

## 六、这个功能值得做吗？

**值得，但要先认清它是什么。**

- ✅ **它适合**：回答「同一食物在不同国家标准下的差异」——这个对做跨境营养标准、国际化产品、学术研究有真实价值。
- ❌ **它不适合**：当成「权威食物营养数据库」用。中国 FCT 只有 1677 条，CoFID 有 31757 条，**覆盖范围差一个数量级**，交叉比对无法补齐覆盖率。
- ⚠️ **它有真实风险**：不同国家的食物定义、采样、检测方法不同（见下方警示）。比对结果必须带免责说明，否则容易被误用。

### ⚠️ 使用警示（必须写进文档和输出）

同一食物在各国数据库中数值不同的**常见原因**：
1. **食物定义不同**（中国「猪肉」是生鲜部位分割肉；CoFID 可能含脂肪比例）
2. **可食部差异**（中国库有 `edible` 字段，CoFID 有 `weighed with skin` 变体）
3. **计算口径不同**（碳水：可利用碳水 vs 总碳水减纤维）
4. **检测方法不同**（火焰光度法 vs ICP-MS 测钠；氨基酸分析法的水解损失）
5. **样本不同**（同一食物 20 个产地采样取均值 vs 单一农场样本）

> **数值差异不等于数据错误。** 交叉比对的正确用途是发现「系统性差异」并追查原因，而不是评判「谁的数错了」。
